# Valuation workflow contracts

Read the subsection for the requested operation: drafting, owner editing, or computation. This file owns the detailed workflow requirements; the [draft skill](../SKILL.md) and [compute skill](../../compute-valuation/SKILL.md) sequence them. The draft review boundary applies to both.

<a id="section-18-7"></a>

## 18.7 Procedures

## Owner-requested quick iteration

When the owner asks for a faster iteration or to check revised numbers first, present the requested input changes after a focused validation instead of completing the full independent-review, app-audit and forecast-record pipeline before handoff. Preserve the prior inputs, clearly label any unfinished review, and update the active inputs when explicitly requested so the owner can inspect them in the app. Do not call an unreviewed proposal financially approved. Full review and archival follow-through can follow when requested; do not continue them in the background by default. This explicit owner direction takes precedence over the standard sequencing below and does not authorize unrelated edits or valuation computation before the owner requests it.

<a id="drafting"></a>

**`draft-valuation <TICKER>`** (internal diagnostics only; stops for owner review before valuation results):

1. Preconditions: `business.md` and `outlook.md` exist; route missing prerequisites only when covered by the owner's request (the root routing rule). If `valuation/assumptions.yaml` exists, redrafting requires `--redraft` or an explicit redraft request; otherwise use the existing inputs for a requested compute or explain the editing options. For an authorized redraft, copy the existing `assumptions.yaml`, `assumptions.md`, and `valuation.md` (if present) byte-for-byte into a unique `history/<timestamp>/` directory. Keep the active files intact while preparing a candidate at `valuation/drafts/<timestamp>/assumptions.yaml`. The initial-draft target is `valuation/assumptions.yaml`. Call the selected path `<ASSUMPTIONS>` below. If the archived file carries a `changelog`, hand the owner-edited cells and values to the analyst: it builds its own sourced view, explains differences in `detail`, and reports both values side by side. This explicit redraft authorization is the exception to keeping owner values fixed; never silently overwrite or silently retain them.
2. Launch one **analyst** subagent with [reader rules](../../../../docs/research.md#section-3), [model requirements](model-spec.md), [assumptions rules](assumptions-spec.md) and the playbook, `business.md`, `outlook.md`, `scorecard.md` if present, the selected target, and read access to the permitted pre-cutoff cache, including prior periods needed for trailing-twelve-month calculations. It writes `<ASSUMPTIONS>` per [§18.4](assumptions-spec.md#section-18-4). Cells that need Damodaran's datasets or the market price (unlevered beta, market debt-to-equity) it leaves `null`, stating the industry or the numerator in the reason. Before launching the analyst, the runner reads the playbook and assembles the rule 16 evidence note, including the [§18.11](model-spec.md#section-18-11) model-fit, accounting and uncertainty assessments, reusing the library and fetching only material valuation-specific gaps. The analyst fetches nothing and sends precise evidence requests to the runner; unresolved gaps follow [§13](../../../../docs/review.md#section-13). Give both analyst and reviewer the evidence note and benchmark sources.
3. The runner fills those cells from the cached datasets ([§18.8](model-spec.md#section-18-8)) and a direct price fetch, recording dataset and price dates in each cell's `source`. Fetch the price without a valuation using `uv run python -c 'import sys; from valuation.market import fetch_price; print(fetch_price(sys.argv[1]))' <TICKER>`. Run `uv run value <ASSUMPTIONS> --validate`, repairing agent-authored errors and handling unsupported inputs under [§13](../../../../docs/review.md#section-13) rather than looping until success. Render the readable draft with `uv run value <ASSUMPTIONS> --render-assumptions`, including when blocked, and regenerate it after edits. Once the narrative and inputs are built, perform the target-specific app check in [§18.10](../../../../tools/valuation/APP_GUIDE.md#section-18-10); repeat it after subsequent changes before handoff, including for REVISE or BLOCKED drafts.
4. Launch one **reviewer** subagent. It writes `review/<QLABEL>-valuation-draft-review.md` with: (a) every base-year and bridge number re-checked against the cached source, listing failures; (b) the 3P test on each story with one line each; (c) consistency checks: the story-to-numbers table present in every computable case, covering every input, each row's number matching its input cell, and every applicable question in [review checklist](review-checklist.md) answered with evidence (rule 14); year-1 growth against the latest reported run-rate (rule 10); the segment build present, sourced and summing to the path (rule 11); sales-to-capital set against the lagged history (rule 12); the margin bridge showing both drag and offsets (rule 13); amortization roll-off addressed; management case built only from recorded guidance; terminal rules respected, including an independently justified mature ROIC and consistent capital definitions; rules 15–16 checked by reproducing each material input bridge and inspecting peer sources, target placement, alternatives and falsifiers; weights sum to 1; and the [§18.2](model-spec.md#section-18-2) transition check, read from `uv run value <ASSUMPTIONS> --diagnostics-only`, recording flags and terminal-versus-final-year cash flows and returns; (d) reader check on the stories and reasons: every reason is one to three plain sentences, working numbers live in `detail`, nothing substantive sits in YAML comments; (e) PASS, REVISE, or BLOCKED under [§13](../../../../docs/review.md#section-13). Both analyst and reviewer read the playbook and applicable topical references, recording their application to material judgments. The reviewer includes [§18.11](model-spec.md#section-18-11) capability/accounting checks and [§18.12](forecasts-and-learning.md#section-18-12) forecast-learning checks. Use [§13](../../../../docs/review.md#section-13)'s two-pass limit and evidence-gap handling.
5. Only after PASS, promote an authorized redraft candidate to the active `assumptions.yaml` and regenerate its `assumptions.md`. Before replacing anything, verify that the active files still match the archived snapshot; if the owner edited them meanwhile, preserve both versions and ask how to reconcile them. Do not recompute or rewrite `valuation.md`; report that it still reflects the prior assumptions. On failure, leave the active files intact and give the candidate path. Freeze an analyst-proposal forecast under [§18.12](forecasts-and-learning.md#section-18-12) after promotion, without valuation results. Commit a passing draft and its forecast record as `value(<TICKER>): draft assumptions as of <QLABEL>`.
6. Report to the owner: the four stories in one line each, the five inputs most worth their attention, anything the analyst could not source, the review verdict, any differences from owner values, the app-check outcome and record, and the exact next step. For a passing draft, direct the owner to read `assumptions.md`, then choose to compute in the app or request `compute-valuation`. For a blocked draft, state what must be resolved first.

<a id="draft-review-boundary"></a>

**Draft review boundary.** The runner and reviewer may compute internal diagnostics through `--diagnostics-only`. It prints JSON containing inputs, operating cash flows, returns on capital, transition checks, stopped/skipped cases, and warnings, without computed asset/equity/per-share values, price-relative valuation ratios, reference valuations, sensitivities, or reverse DCF. Do not use ordinary `--dry-run` or full `--json` output while drafting. Do not show valuation results to the analyst or owner or write `valuation.md` before the draft has been presented for owner review and the owner subsequently requests computation or chooses it in the app. No extra confirmation is needed for that subsequent compute request.

<a id="owner-editing"></a>

**Owner editing (the app, [§18.10](../../../../tools/valuation/APP_GUIDE.md#section-18-10)).** The owner does not edit YAML by hand. `uv run --extra app valuation-app` opens a local page that shows every input with its reason, recomputes live through the same engine, and on **Save** writes changed values back into `assumptions.yaml`, preserving reasons, sources, and comments, appending a `changelog` entry per changed cell (with the owner's note if given), and regenerating `assumptions.md`. **Write valuation.md** in the app runs the same code path as `compute-valuation` step 2; **Commit** runs step 4. An agent that later reads a YAML with a `changelog` must treat owner values as fixed except for explicitly requested edits or the authorized-redraft procedure above. Do not ask the owner to type YAML.

<a id="computation"></a>

**`compute-valuation <TICKER> [--set path=value ...] [--dry-run]`**:

1. Preconditions: `valuation/assumptions.yaml` exists and the owner has requested computation after the draft-review boundary. Route a missing draft only when the request covers drafting, then stop at that boundary. Pass all supplied `--set` overrides unchanged to both `uv run value <TICKER> --validate [--set ...]` and computation; they apply in memory only. Inspect errors and stopped cases, not just the exit code. Fix no YAML in this workflow: a judgment change goes to the owner. An unresolved validation error blocks computation; report it without asking the owner to repeat valid overrides. If the outlook is newer than the inputs, disclose staleness and proceed.
2. Run `uv run value <TICKER> [--set ...]`, adding `--dry-run --json` for a requested dry run so the current result and its metadata can be inspected. A normal run computes successfully before the engine archives the previous pair and writes `valuation.md` and `assumptions.md`; do not archive a second time in the runner. A dry run writes and archives nothing. Use the bounded fetch retries and documented fallbacks in [§18.8](model-spec.md#section-18-8); do not invent a market input when they fail.
3. Inspect the current result: the new `valuation.md` for a normal run, or the current JSON for a dry run (never a stale file). Check that stopped/skipped cases are explained, warnings are reported, and market dates and sources are present or explicitly unavailable for manual inputs. A skipped management case must match its recorded `computable: false` reason. Report any defect and do not claim completion or commit an unchecked report.
4. After a successful normal run and sanity read, freeze an owner-compute forecast under [§18.12](forecasts-and-learning.md#section-18-12), recording the exact input bytes and effective overrides used. A missing or ambiguous learning record is disclosed separately rather than silently presented as complete. Then commit `value(<TICKER>): compute <QLABEL> rev N` (count prior compute commits for this quarter, not every history folder, since redrafts also create history). Never commit on `--dry-run`.
5. Report to the owner in a few lines: per-share value per case against price and date, weighted value when available, terminal-value share, reverse-DCF growth, every warning, and stopped/skipped cases. No interpretation beyond that. A dry-run report comes from that run's output, not the saved report. If owner changes exist, report changes since the last compute where that comparison is available; do not substitute unrelated history entries.

The refresh skill never re-values. When `refresh-company` runs on a company that has a `valuation/` folder, its report tells the owner the valuation is now as of an older quarter.
